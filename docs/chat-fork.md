# Conversation forks

Each assistant reply in the editable conversation view has a Fork conversation icon in its action row, alongside copy, regenerate, and delete. The action creates and opens a new local conversation containing only the selected reply and its ancestors. Later messages and alternate replies are excluded. Selecting an older reply version forks that exact version. Message IDs and parent links are independent, and the copied reply becomes the current message. Message contents, timestamps, attachments, model, reasoning settings, and workflow/template selections are retained. The new conversation starts with sharing disabled. Completed workflow records and local attachment files remain references to their existing resources; they are not duplicated or executed. User messages and sharing previews do not show the fork action.

The copy is a configuration snapshot. Its initial Agent version is current so opening it does not immediately replace its saved settings with the Agent defaults. Later Agent updates follow the existing conversation behavior.

Forking does not send a message or call a model. Loading, receiving replies, and duplicate clicks disable the action; only the clicked action shows a loading indicator. The backend requires an assistant message in the source conversation and rejects pending, generating, or running-workflow states along its ancestry. Invalid ancestor chains return an error. Other branches and later messages do not affect the selected context. Conversation, messages, and relations are written in one transaction, so failures leave no partial copy. Leaving the page invalidates pending navigation responses. Unsent text and attachments remain in the reused conversation view when opening the copy.

Coverage: `backend/tests/test_chat_fork.py` verifies graph remapping, snapshot preservation, source isolation, input validation, and rollback. `frontend/tests/chatFailures.test.js` verifies successful navigation, busy states, failures, duplicate clicks, drafts, and stale responses.
