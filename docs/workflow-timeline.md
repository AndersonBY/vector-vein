# 工作流节点时间线

运行页默认只显示正常输出。需要排查问题时，点击输出标题旁的“调试信息”，按需展开“节点时间线”；再次点击“收起调试信息”即可隐藏。每次重新运行、打开历史记录或清除记录时，调试信息恢复隐藏。

时间线展开后，运行期间每秒刷新节点状态；完成、失败后保留结果，打开同一条历史记录也能按需查看。后台执行记录不受展示开关影响。

时间线按节点分别显示状态、耗时、开始时间和结束时间。并行节点各自更新，不会因其中一个完成而把另一个标为完成。顶部“已结束”数量包含成功、失败和跳过的节点，并不代表成功数量。

| 状态 | 含义 |
| --- | --- |
| 待执行 | 尚未开始的节点。 |
| 执行中 | 节点已开始执行。 |
| 等待中 | 节点已安排稍后重试，例如等待子工作流完成。 |
| 成功 | 节点正常返回。 |
| 失败 | 节点发生错误，具体原因显示在运行状态提示中。 |
| 已跳过 | 条件分支明确跳过此节点。 |
| 未执行 | 工作流失败后没有开始的节点。 |
| 未知 | 旧记录缺少足以确定状态的执行证据。 |

耗时是从节点首次开始到最终结束的经过时间，包括节点内部等待或重试间隔。执行中的耗时随时间更新。触发器、注释和忽略的节点不计入执行节点总数；动态展开的子节点在执行时加入时间线。

旧记录没有新时间线字段时，使用原有节点状态和耗时显示已有证据。没有记录的时间显示 `—`，不会补造开始或结束时间。重新运行会创建新记录并清除上次的执行状态、失败、跳过和耗时，原历史记录保持原有结果。

## 数据与接口

每条运行快照的 `node_timeline` 是以节点 ID 为键的对象。单个节点记录如下：

```json
{
  "node_id": "request",
  "node_type": "HttpRequest",
  "title": "读取数据",
  "task_name": "tools.http_request",
  "status": "SUCCEEDED",
  "started_at": 1793000000000,
  "finished_at": 1793000002500,
  "run_time": 2.5
}
```

时间戳单位为毫秒，`run_time` 单位为秒。未开始或尚未结束的时间为 null，`title` 仅在有自定义名称时提供。时间线只增加节点标识、名称、状态和时间，不复制节点输入、输出、代码或凭据。

`workflow.check_status` 的 `202` 响应在 `data.node_timeline` 提供实时状态，同时保留已有 `finished_nodes` 字段。活动运行的 `workflow_run_record.get` 同样提供最新时间线。运行终止时，将时间线与原运行快照一起存入数据库，历史查看无需实时缓存。

实时状态通过已有本地缓存按运行原子合并，24 小时过期。时间线更新失败不会重新执行节点，也不会替换原来的执行错误。它用于展示执行过程，不提供中断恢复、取消或剩余时间估计。

## GUI 验收

1. 运行含两个并行慢节点的工作流，确认默认只显示正常输出。点击“调试信息”，确认两者同时显示“执行中”，耗时增长；先结束的节点显示“成功”，另一个继续执行。点击“收起调试信息”后时间线隐藏。
2. 等待工作流完成，打开该条历史记录，核对各节点的状态、开始时间、结束时间和耗时。
3. 让一个节点失败，确认保留同层其他节点的执行结果，依赖失败节点且尚未开始的节点显示“未执行”。
4. 重新运行，确认旧失败和耗时被清除，历史中的上一条记录仍保留。
5. 查看条件分支跳过节点和更新前的旧记录，确认“已跳过”与“未执行”区分，无记录的时间显示 `—`。
